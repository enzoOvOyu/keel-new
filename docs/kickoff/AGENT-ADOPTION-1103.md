## 采用链路及已发现问题

前端 SourceAgentPanel 调用 HttpKickoffProvider.adoptSourceAnalysis，POST analysis/adopt；后端在工作区锁、源版本与输入版本校验后合并物理实体、输入、证据，最后同事务提交并写 adoptedTableIds；analysis GET 据此排除已采用表。

现场只读数据库观察到：一个采用事务在读取 eng_evidence 后长时间 idle in transaction，另一个请求在 SELECT kickoff_workspace FOR UPDATE 等锁，工作区revision仍2且任务无采用标记。尚未提交，所以切页重新查询仍返回待采用候选。

kickoffAgentMergePhysical.addEvidence 对每条候选遍历整张证据表，反复对双方候选行做JSON摘要；findDevice、findPort也线性遍历。端口14308、连接7154会放大为平方级处理，且处理期间持事务锁。此结论来自代码与现场等待状态；未做CPU profile，不将单一热点冒称唯一根因。

## 后端修复（已实施，待部署验证）

1. 按候选行内容摘要预建证据索引，摘要每行算一次，保留同内容重复行的全部来源；不能直接以过滤后的行号替代原行号。
2. 设备SN、设备+端口名建立查找索引，沿用现有歧义判断及稳定ID。
3. 不依赖现有请求反复重试；采用重复提交应尽快返回已有处理状态，不能长时间排队持锁。
4. 先评估上述最小优化；若采用仍超过HTTP请求窗口，再设计持久异步采用任务及202/状态回执，沿用版本校验、事务与证据，不用前端定时器伪造成功。
5. 验证旧MM候选复用、14类采用计数、版本/来源保护与CMDB回执，避免重跑AI。
