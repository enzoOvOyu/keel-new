有明确的优化空间。建议采用 **“先优化批量写入和重复校验，再调整来源数据存储；保留现有 PostgreSQL、事务和 Outbox”** 的方案。

先纠正一个时间口径：刚才的 **934秒是整轮采用、核对、重复采用和CMDB发布验证总耗时**，不能全部算成CMDB写入时间。正式优化时需要分别计时。

目前已完成代码核查，本轮只给方案，没有修改实现。

**1. 当前实际瓶颈**

这批数据包含809台设备、14308个端口、7154条连接。仅这三类就涉及约2.2万个对象，还要写入机柜、关系、属性来源、版本和事件。

| 已确认的实现问题 | 影响 |
|---|---|
| `projectAsset` 对每个对象查询存在性和项目归属，再调用 `UpsertAsset` | 同一对象重复查询 |
| 每个对象分别写BOM关联、资产、版本、来源和事件 | SQL数量随对象数快速增长 |
| `UpsertAsset` 已写属性来源，工程发布随后又写一次来源 | 重复执行插入和唯一约束检查 |
| 每条关系调用 `PutRelation`，分别查询两端类型、权限范围、加锁、校验和写入 | 大量端接关系放大重复工作 |
| 同一设备或端口被多条关系反复引用、查询和锁定 | 相同数据被重复处理 |
| 来源记录逐字段保存项目、操作者、审批和证据等公共信息 | 数据和索引写入量较大 |

其中属性来源已经使用了**单对象内的 `pgx.Batch`**，但本质上仍是多条SQL。下一步应该扩大到跨对象的集合写入，不能只是再包一层Batch。

**2. 第一优先级：专用批量发布路径**

保留单对象编辑接口，给开局发布增加批量路径，共用已有业务规则。

建议处理顺序：

```text
冻结本次发布范围
→ 汇总设备、端口、线缆、机柜及关系
→ 批量读取已有对象与来源
→ 批量校验身份、项目范围和关系
→ 计算实际差异
→ 批量写资产、属性来源、关系、版本和事件
→ 提交事务与发布回执
```

具体改动：

- 一次读取本次涉及的对象、类型、项目归属及已有规划/观测状态，建立本次任务内的查询索引。
- 设备、端口、连接等分类批量写入，避免每个对象重新走完整通用接口。
- 合并两处属性来源写入，让每条来源事实只处理一次。
- 公共Schema和关系定义每次任务读取一次。
- 校验与差异计算尽量放在正式写事务之前；提交时重新核对版本和必要约束。

这些任务内索引只覆盖本次发布范围，不需要把全库缓存进内存或Redis。

**3. SQL优化：真正减少语句数量**

优先采用两种方式：

| 场景 | 建议 |
|---|---|
| 中等批次、多字段写入 | `INSERT … SELECT FROM jsonb_to_recordset(...)` 或 `UNNEST` |
| 大批量资产、属性和关系 | `pgx.CopyFrom` 写入事务内临时表，再执行集合校验及合并 |

例如，先将待写入对象送入临时表，然后通过JOIN统一检查项目归属，再批量插入或更新正式表。

关键规则：

- `ON CONFLICT DO UPDATE` 增加实际变化判断，例如 `IS DISTINCT FROM`，减少无效更新、WAL和索引维护。
- 原有资产仅新增规划证据时，不重写Observed实际状态。
- 属性没有变化但新增了合法来源时，只增加必要的来源关联。
- 外键、身份唯一约束、项目隔离继续保留。

**关系也必须批量处理：**

- 一次JOIN检查全部连接两端是否存在、类型是否允许、是否属于同一授权项目。
- 同时检查“本批关系之间”和“本批与已有关系之间”的端口占用冲突。
- 对需要保护的资产ID去重、按固定顺序加锁，避免逐关系重复加锁。
- 包含/父子关系单独做环路检查；普通线缆端接不走无关的层级图校验。
- 批量结束旧规划关系、建立新关系，保留人工确认和观测关系。

**4. 数据库格式：保留结构化核心，优化来源存储**

当前不建议把CMDB整体改成一个大JSON，也不建议换数据库。

| 数据类别 | 推荐形式 |
|---|---|
| 稳定身份、类型、名称、项目归属、生命周期、版本 | 明确列与关系表 |
| 设备—端口、端口—线缆、设备—机柜 | 明确关系及约束 |
| 型号差异、可扩展属性 | 有Schema约束的JSONB |
| 原始工作簿、完整AI日志、大型分析产物 | MinIO |
| 正式状态、任务进度、发布回执 | PostgreSQL |

`cmdb_field_source` 可以分两步优化：

- **先不改表**：去除重复写入，跨对象批量插入，只保存新增或变化的来源事实。
- **仍有明显写放大时再改表**：增加公共来源记录，统一保存发布ID、操作者、审批状态等；字段来源只保存资产、字段、值、来源ID以及字段特有的单元格证据。

第二步必须保留字段级追溯能力，不能为了省空间丢掉来源。

版本快照也先保持现状。只有测量确认历史快照成为主要负担后，再考虑“变化记录＋定期完整快照”，避免本次变成数据库重构。

**5. 索引优化：针对当前SQL补齐**

目前已有资产、项目范围和关系端点索引，不应重复创建。

重点验证以下查询是否缺少合适索引：

- 查询某资产是否存在非规划来源。
- 按项目、关系定义、端点查找有效规划关系。
- 发布事件幂等检查。
- 按发布批次读取回执和来源。

候选方向包括：

```sql
-- 对应已有非规划事实检查
(asset_id) WHERE fact_layer <> 'planned'

-- 对应有效关系查找
(project_id, definition_id, from_uid) WHERE valid_to IS NULL
(project_id, definition_id, to_uid) WHERE valid_to IS NULL
```

这些只是候选。先看实际执行计划，再决定是否建立；新增索引也会增加写入成本。

**6. 任务批量与并发**

第一阶段保留一个发布事务，事务内部按批次发送数据。**分批发送不等于分批提交**，这样不会让下游读到半套拓扑。

初始批次建议：

- 资产：500～1000个。
- 属性来源、关系：1000～5000条。
- 同时限制每批编码后的字节数，避免少量大对象撑爆内存。

这些是调优起点，不是固定常量。

并发策略：

- 解析、构造写入数据、部分纯计算校验可以有限并行。
- 同一项目、同一批资产的发布保持受控串行。
- 无共享写入对象的不同项目可以有限并行。
- 不为每个设备启动goroutine并发写数据库。

任务继续复用现有持久队列与Outbox，增加可理解的进度：校验、资产写入、关系写入、提交回执。进度数量必须来自实际处理数量。

如果批量优化后，超大项目仍存在不可接受的长事务，再考虑“持久暂存批次＋完成后原子切换发布版本”。这会影响所有读取接口，属于第二阶段，不建议现在就做。

**7. 实施顺序与验收**

建议分三批完成：

1. **计时和去重**：记录各阶段耗时、SQL调用数；消除重复资产查询和重复来源写入。
2. **批量发布**：资产、来源、关系、版本和事件改为集合处理，保留事务与权限规则。
3. **按测量补索引**：若来源写放大仍显著，再实施公共来源记录拆分。

继续使用刚才这份已保存的分析产物对比，不需要重新调用AI。验收同时检查：

- 809设备、14308端口、7154连接及805机柜关联完整保留。
- 身份、线缆长度、来源、版本和回执一致。
- 重复发布没有重复对象或无意义版本增长。
- 规划值不覆盖Observed或人工确认值。
- 分别报告采用、CMDB写入和总耗时，并对比SQL调用数量。

**优先收益应来自减少数据库操作次数和重复工作。**先把这条路径做成真正的批量发布，再决定是否需要更大的存储或架构调整。
