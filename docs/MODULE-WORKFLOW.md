# 模块维护与交付规则

## 权威与冲突

1. 用户最新确认的目标和约束决定范围。
2. `docs/modules/<module>.md` 记录该模块当前产品要求、边界、交互和剩余事项；旧 PRD 不再作为五个已整理模块的上位任务清单。
3. `docs/openapi.yaml` 是本分支唯一机器可读 HTTP 契约；生成类型不手工改。`docs/api/*.md` 只说明使用语义，不复制完整 DTO。
4. 路由、Adapter、Handler/Service 是“实现存在”的证据；部署报告是“版本已运行”的证据；定向验收记录是“具体行为已验证”的证据。这三者都不能自动改写产品要求。
5. 发生差异时记入 `DECISIONS.md`，写明需求/协议/实现/环境哪两项冲突及最小后续动作。不要默默选择旧文档，也不要为了与旧 PRD 对齐而改代码。

## 一次模块变更的最小闭环

- 阅读 HANDOFF 当前快照 → 目标模块 → 对应 API 语义与登记 → 直接调用链；不重复遍历全仓。
- 确定本次输入、输出、权限、页面动作、验收和不包含的能力。复用统一身份、CMDB、工程发布、作业平台、Monitor；不建立平行事实库。
- 新能力可先做前端契约/Mock；已经真实化的模块沿真实 Provider 迭代，不能恢复模拟回退。其他模块不会因本模块上线自动变成真实实现。
- 修改协议时，在同一变更中同步 OpenAPI、生成类型、受影响 Handler/Service/Adapter、API 语义和注册表；不为原型擅自改全平台 Schema。
- 仅做任务必要验证。测试节奏遵循用户安排；本次纯文档仅做链接、注册表一致性和 diff 检查。编译、模拟交互、HTTP200、真机验收分别记录。
- 模块可独立发布；部署是单独动作，必须沿已有授权和回退方案，不能从设计或历史记录推导授权。上线后记录精确 revision、环境、证据和未验收项。
- 更新模块页的“当前状态/剩余事项”，替换过时句子；HANDOFF 只保留当前交接。阶段过程留 Git/原报告，不继续向现状文档尾部堆叠里程碑。
- 完成一项有意义修改创建 Git 提交。远程只使用 `enzoOvOyu/keel-new`；本次文档整理不推送、不合并 main。

## 状态记法

| 维度 | 最低记录 |
|---|---|
| 设计 | 当前要求；尚未定案单列 |
| 实现 | 分支/提交、入口文件、实际边界；草稿不是完成 |
| 部署 | 环境、精确发布版本、发布证据；分支预览不是主环境上线 |
| 验证 | 场景、数据性质、版本、结果和限制；没做写 NOT RUN |

一个模块允许“核心上线、扩展待开发、生产验收未运行”同时成立。模块完成不等于全部机器接口、现场设备或所有性能目标完成。

## 跨模块不变量

- Kickoff 发布工程规划；CMDB 统一稳定身份及资产关系；拓扑读取事实；Fabric 编译/校验/审批；作业平台执行；Monitor 提供观测。没有证据不补造网络参数或运行状态。
- 原始文件不可变、字段/对象来源可追溯；AI 候选须审核。数量不能生成虚假 SN/MAC/IP；真实原件及凭据不进 Git、fixture 或外部提示词。
- 已发布事实、期望配置、实际配置和运行观测分层；unknown/unsupported/stale 与 PASS 分开。产物必须绑定输入、版本与目标。
- 统一 Session/RBAC/项目及设备范围；前端隐藏不是授权。关键变更保留审批职责分离、审计、幂等及并发版本校验。
- `maintained` 严格 IPMI-only，不通过 SSH/Agent/Redfish、重试或第三方代理绕过。审批/签署资格未决不自动按 admin 放行。
- 继续保留六阶段：开局配置→网络就绪→装机→验机→NCCL→优雅退场；Fabric 七个内部环节不是新主链。
